# 开发管线（走法定义）

> 本文件回答一个问题：**一个改动进了门，按什么走法走到归档**。
> 两条铁原则：①分类矩阵是编排层内部判据——对话里永远说人话（「这个我打算先补个回归测试再修，你确认」），不向用户暴露类型术语；②已覆盖的机制不重复定义——建档/拆分/审查/验收归档走既有 new-task/split/merge/accept，本文件只定义「选哪条走法、每条走法的出口条件」。
> 血缘：2026-09-28 用户拍板 taskflow 替代 superdx 路线，吸收其迭代分类与阶段矩阵；词汇全部 taskflow 原生（不引入字母阶段）。

## 改动分类矩阵（编排层判据）

| 用户在说什么 | 内部类型 | 走法 |
|---|---|---|
| 「XX 乱了/不对/不好用」——行为与预期不符 | bug | **前置问句：预期行为在 spec/PRD/conventions 有据？**无据 → 先走隐性升级/需求确认对口径（候选口径并列呈报），禁以测试断言自造预期（实证：排序 spec 从未定义，模型按先验断言创建时间倒序修到绿，验收被打回「我要拼音序」——测试把第一判断固化为断言）；有据 → ①判性质（硬规则 9：先查为何复发，禁止直接补丁）②**回归测试先行**：先写红测试锁住 bug，再修到绿 ③修复④走验收 |
| 「帮我加 X」——PRD 没有的新能力 | new_feature | 需求溯源三选一（无文档先补/呈用户决定）→ 归入 vs 另开 → 规模分档 → 产物链 |
| 「把 X 改成 Y」——改 PRD 已有功能的行为 | req_change | 需求变更门：呈「原口径 → 新口径 → 影响」，拍板前不动工 → spec+PRD 同步改 → `req-confirm` 落痕 |
| 「文档/规则/约定更新」——不改代码行为 | docs | 轻走法：直接改 + checkpoint 一条 + findings 记一行；不建 worktree、不拆分（纯文档任务按 small 裁剪走 merge） |
| 「重构/优化/清理」——不改外部行为 | refactor | **行为不变证明前置**：开工前既有测试全绿留基线，收口同一套测试仍全绿；过程中夹带行为变更 = 当场改判 req_change/new_feature，禁混档 |
| 纯文案/样式/格式微调 | trivial | 表面微调走法（SKILL.md 反馈分类既有）：直接改 + findings 一行 |
| 工程工具/一次性脚本（"写个脚本批量处理"——不改产品行为） | tooling | small 档 + AC 豁免注记（对齐硬规则 27）+ findings 落痕，免 PRD 溯源保留验收 |

**升级路径**（分类判错不硬撑，当场升并告知用户）：

- 修 bug 时发现 PRD/设计本身有误 → 升 req_change（= 既有隐性升级门，原口径/新口径/影响呈报拍板）。
- new_feature 规模大（≥5 个新用户故事）且动核心架构（非增量追加）→ 升 large 档全流程（关键决策逐项拍板 + spec 整体确认后才许拆分）。
- refactor 中想改行为 → 停手，改判 req_change。

**改动两道前置判定（动手与呈报纪律，牵连排查/数据边界）**：

- **牵连排查（影响面分析）**：凡改动触及共享单元——被多处引用的函数/组件、接口契约（入参/响应/异常）、表结构与字段、prompt 模板、共享配置——动手前先列消费方清单（grep 引用或代码图谱 impact 工具，盘点机制同硬规则 14）；改动呈报必含「**影响面：已核 N 处（列名）；未核 0 处**」，禁只陈述改动本身等用户问牵连。分析由领域技能引导：挂 impact-analysis（影响面）技能，缺失跑 `tf.mjs skills 影响面` 检测，按硬规则 22 呈用户选装；等待期间按本节清单手工执行不停摆。
- **数据边界**：数据驱动功能（统计/对比/榜单/推送/导出/综述）改动或新建时，枚举输入形态至少五类：正常/空集/单条/首期无上期（或同构的「无参照」形态——即数据真空（空数据场景））/异常值；每个真空形态的行为必须显式——降级不渲染+状态语、跳过该段、或显式占位，禁三种静默：**算了不传**（构建器产出但未进消费方输入）、**传空容器假装有料**（空数组/空串当有效数据传）、**没数据硬凑**（编「较上期持平」类无据对比句）。环比原则（用户拍板原话级）：**有数据就对比，没数据不硬凑**——上期有数据→传对比素材+要求综述含变化段；上期真空→不给对比素材也不硬凑。分析由领域技能引导：挂 data-boundary（数据边界）技能，缺失跑 `tf.mjs skills 数据边界` 检测，按硬规则 22 呈用户选装；等待期间按本节清单手工执行不停摆。

## 从零开工（全新项目）

用户说「做个新项目 / 从零开始」时不进常规分档，走**六问链**——每问一个大白话问题，过一问锁一问（checkpoint 留痕），全答完才开工：

| # | 问题 | 做什么 | 出口条件 |
|---|---|---|---|
| 1 | **做什么？** | 结构化访谈收敛用户故事 + 功能需求（PRD） | 用户故事**逐条点头**定稿 |
| 2 | **怎么做？** | 设计文档 + 关键决策（贵翻项逐项拍板：技术栈/存储/部署环境；便宜项推荐+注记） | 方案整体确认 |
| 3 | **长什么样？** | 有 UI 才走：原型验收（自查硬流程照 prototype-selfcheck）；无 UI 跳过 | 原型用户验收 |
| 4 | **留点什么？** | 沉淀问题：可复用流程 → managed skill（也可后置到首次归档） | 明确「沉淀」或「不沉淀」 |
| 5 | **开工** | 项目引导（conventions 引导生成）→ 建档建 worktree → 拆分派发 | 既有确认门槛（建档/派发两道） |
| 6 | **交付** | merge 审查 → 部署 → 验收 → 归档 | 既有 merge 全流程，零新词 |

六问挂 omp Todo 六项——过一问锁一问 = 勾一项（SKILL.md「会话工作台」）。

**产物格式委托项目**：PRD/设计文档「长什么样」由项目 conventions 定义（各项目自有文档形态，如自定义 Stage 划分），taskflow 只定义顺序、出口条件与门控——保持跨项目通用。

## 拓扑变更链（拆套/转正/迁移/新增环境，2026-10-26 沉淀）

「把一套拆成两套」「测试环境转正式」「换库/换存储」「新增一个部署环境」类需求**不进常规分档**（它们不是开发任务：不写业务代码；也不是单次部署：改的是环境之间的边界），走**六步链**——每步产出落 spec，过一步锁一步：

| # | 步骤 | 做什么 | 出口条件 |
|---|---|---|---|
| 1 | **现状拓扑实证** | 逐套列出当前连接的每个外部资源（数据库/对象存储/消息队列/第三方服务），来源=运行中配置而非记忆（读 compose/`.env`/启动参数） | 现状对照表成立，与实际运行一致 |
| 2 | **目标拓扑定义** | 逐套定义变更后应连接的资源，逐项对照**资源交付文档/台账**；与任何资源交付文档不一致 = 停下呈报，禁自行取舍 | 用户逐项确认目标对照表 |
| 3 | **差集与迁移设计** | 现状→目标的差集：哪些连接要切、哪些数据/资产要搬、搬的方式与量级（决定停写窗口时长）；**环境间共享任何资源必须显式拍板，禁默认共享** | 迁移步骤清单 + 窗口时长估算，用户确认 |
| 4 | **回滚线** | 每个切换动作的回退方式（旧连接串备份/旧资源保留期）；回滚演练成本 > 切换成本时显式注记 | 回滚方式落 spec「风险与红线拍板留痕」节 |
| 5 | **执行** | 低峰窗口按清单逐条执行；资产搬迁（数据/对象）先行于连接切换；每步带写后探针 | 既有确认门槛（远程操作清单逐条确认） |
| 6 | **边界验证 + 收尾** | 部署验证清单照常 + **边界断言**（切后核「实际连接是否=目标拓扑」，一条 SQL/读配置级）+ 功能探针；旧环境数据按回滚线保留期满后再退役 | 边界断言绿 + 用户验收 |

**配套**：spec.md「环境边界对照表」节（拓扑变更类任务必填）；挂账语义（「等资源到位后切」）触发**挂账强制立项**承载。

## 测试红线（执行矩阵详见 testing.md）

- 修 bug = 回归测试先行（先红后绿），不是修完「顺手补个测试」。
- 代码任务 merge 阶段二查测试先行动证（v2.33.0：提交顺序证据）。
- 后端 TDD / 数据迁移 / 前端测试 / 文档同步的强制矩阵与性能反模式：**testing.md §九**（merge 阶段二机械核对）。
