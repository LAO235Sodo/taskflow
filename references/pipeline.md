# 开发管线（走法定义）

> 本文件回答一个问题：**一个改动进了门，按什么走法走到归档**。
> 两条铁原则：①分类矩阵是编排层内部判据——对话里永远说人话（「这个我打算先补个回归测试再修，你确认」），不向用户暴露类型术语；②已覆盖的机制不重复定义——建档/拆分/审查/验收归档走既有 new-task/split/merge/accept，本文件只定义「选哪条走法、每条走法的出口条件」。
> 血缘：2026-09-28 用户拍板 taskflow 替代 superdx 路线，吸收其迭代分类与阶段矩阵；词汇全部 taskflow 原生（不引入字母阶段）。

## 改动分类矩阵（编排层判据）

| 用户在说什么 | 内部类型 | 走法 |
|---|---|---|
| 「XX 乱了/不对/不好用」——行为与预期不符 | bug | ①判性质（硬规则 9：先查为何复发，禁止直接补丁）②**回归测试先行**：先写红测试锁住 bug，再修到绿 ③修复④走验收 |
| 「帮我加 X」——PRD 没有的新能力 | new_feature | 需求溯源三选一（无文档先补/呈用户决定）→ 归入 vs 另开 → 规模分档 → 产物链 |
| 「把 X 改成 Y」——改 PRD 已有功能的行为 | req_change | 需求变更门：呈「原口径 → 新口径 → 影响」，拍板前不动工 → spec+PRD 同步改 → `req-confirm` 落痕 |
| 「文档/规则/约定更新」——不改代码行为 | docs | 轻走法：直接改 + checkpoint 一条 + findings 记一行；不建 worktree、不拆分（纯文档任务按 small 裁剪走 merge） |
| 「重构/优化/清理」——不改外部行为 | refactor | **行为不变证明前置**：开工前既有测试全绿留基线，收口同一套测试仍全绿；过程中夹带行为变更 = 当场改判 req_change/new_feature，禁混档 |
| 纯文案/样式/格式微调 | trivial | 表面微调走法（SKILL.md 反馈分类既有）：直接改 + findings 一行 |

**升级路径**（分类判错不硬撑，当场升并告知用户）：

- 修 bug 时发现 PRD/设计本身有误 → 升 req_change（= 既有隐性升级门，原口径/新口径/影响呈报拍板）。
- new_feature 规模大（≥5 个新用户故事）且动核心架构（非增量追加）→ 升 large 档全流程（关键决策逐项拍板 + spec 整体确认后才许拆分）。
- refactor 中想改行为 → 停手，改判 req_change。

## 从零开工（全新项目）

用户说「做个新项目 / 从零开始」时不进常规分档，走**六问链**——每问一个大白话问题，过一问锁一问（checkpoint 留痕），全答完才开工：

| # | 问题 | 做什么 | 出口条件 |
|---|---|---|---|
| 1 | **做什么？** | 结构化访谈收敛用户故事 + 功能需求（PRD） | 用户故事**逐条点头**定稿 |
| 2 | **怎么做？** | 设计文档 + 关键决策（贵翻项逐项拍板：技术栈/存储/部署环境；便宜项推荐+注记） | 方案整体确认 |
| 3 | **长什么样？** | 有 UI 才走：原型验收（自查硬流程照 prototype-selfcheck）；无 UI 跳过 | 原型用户验收 |
| 4 | **留点什么？** | 沉淀问题：可复用流程 → managed skill（也可后置到首次归档） | 明确「沉淀」或「不沉淀」 |
| 5 | **开工** | 项目引导（conventions 引导生成）→ 建档建 worktree → 拆分派发 | 既有确认门槛（建档/派发两道） |
| 6 | **交付** | merge 审查 → 部署 → 验收 → 归档 | 既有 merge 全流程，零新词 |

六问挂 omp Todo 六项——过一问锁一问 = 勾一项（SKILL.md「会话工作台」）。

**产物格式委托项目**：PRD/设计文档「长什么样」由项目 conventions 定义（各项目自有文档形态，如自定义 Stage 划分），taskflow 只定义顺序、出口条件与门控——保持跨项目通用。

## 测试红线（执行矩阵详见 testing.md）

- 修 bug = 回归测试先行（先红后绿），不是修完「顺手补个测试」。
- 代码任务 merge 阶段二查测试先行动证（v2.33.0：提交顺序证据）。
- 后端 TDD / 数据迁移 / 前端测试 / 文档同步的强制矩阵与性能反模式：**testing.md §九**（merge 阶段二机械核对）。
