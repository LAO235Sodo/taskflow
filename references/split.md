# 拆分与子代理派发（medium / large 档）

**何时拆**：涉及 ≥3 个独立关注点，或 ≥2 个子系统可并行，或用户明确要求。small 档不拆。

**拆分粒度（每个实现单位）：**
- 单一职责，一句话能说清
- 可独立验收（有明确验收命令/标准）
- 涉及文件集合明确、尽量不与其他子任务重叠
- 小步可验证（2-5 分钟级别的人类工作量粒度）

**施工纪律（步骤级，v2.51.0；拆分时写进各子任务 spec 的实现步骤，不拆分直接干时由 new-task.md 第 11 步触点自查——两路都可达）**：
- **粒度红线**：单个实现步骤预计触碰 >5 个文件或跨 >2 个**独立子系统（操作定义：可独立构建/发布/演进的产物边界——如前端 web 包、后端 jar、独立服务各算一个；同一模块内的层不算）** → 必拆；步骤标题或要点出现「并且/同时/且/**顿号并列两个动词**」= 其实是两步，拆（防字面规避）。**内聚豁免（封闭判据，非开放列举）**：仅限**单点源扩散**——改动源头是单点（一个 token 定义 / 一个共享类型 / 一处重命名），其余文件全是机械跟随、无独立逻辑判断；注记「内聚不可分：<单点源是什么>」后可整体一步。多点逻辑改动不适用（对抗审查样例：重构 service 层 12 文件 ≠ 单点源扩散——每处都是独立判断，必须拆）。
- **依赖图排序**：实现步骤自底向上——数据模型/表 → 接口契约 → 业务逻辑 → 调用方/前端；任何步骤不得依赖尚未在前序步骤创建的东西（不按「从重要到次要」排）。
- **垂直切片**：按一条完整功能路径切步（建表 + 接口 + 最小可用逻辑 = 一个可验证切片），不按层横切；每步收尾系统处于可编译、可验证状态。
- **验证锚点**：每 2~3 步显式写一个验证锚点（「此处构建应通过」「此处接口应能跑通基本读写」），**单步任务也须有一个收尾锚点**（「此步完成 = <可观察结果>」）——执行者按锚点逐步验证，不闷头跑到底；「单步纪律天然满足」的注记须附触碰文件数（可核对）。

拆票模式可联动 `to-tickets`（tracer-bullet 子任务 + 阻塞边声明，见 domain.md 阶段轴），依赖关系复杂时尤其值得。

**流程：**

1. 每个子任务从 `templates/subtask-spec.md` 生成 `subtasks/<n>-<slug>/spec.md`。**必须自包含**：执行者只能依赖这份文档与代码库，不依赖任何会话记忆（背景一句话、目标、验收、涉及文件、约束与禁止事项、产出要求）。
   涉及 UI 的子任务：按 references/domain.md 把 `frontend-design` 的设计方向要求写进约束节；**前端原型实现子任务必须附 DESIGN_SPEC_EXTRACT 规格表（`spec-extract.json` + `spec-extract.md` 结构树摘要，模板「设计规格表」节）——执行者对照源码级规格实现，编排层凭记忆转述原型 = 违规（四轮返工实证）**。
2. **★先 checkpoint 整个计划，再派发★**（铁律 2）。
3. **隔离判定表：**

| 情况 | 隔离方式 |
| --- | --- |
| 子任务相互独立、文件集合可能重叠、要并行 | 每个子任务独立 worktree + 分支：`git worktree add ../<repo>-<task-id>-<n>-<slug> -b task/<task-id>/<n>-<slug>` |
| 子任务有依赖（B 需要 A 的产物） | 串行（按依赖序），同一任务 worktree 内执行 |
| 纯只读调研（不改代码） | 不建 worktree |

   **并行准入预检（DISPATCH_OVERLAP，v2.59.0）**：并行派发（下方场景①）前必跑 `node <skill目录>/scripts/tf.mjs overlap <task-id>`——子任务 spec「## 涉及文件」反引号路径两两求交（matchPath：目录声明尾 / 覆盖子孙）；红（重叠对点名）= 不准并行：改串行（同任务 worktree 按依赖序）/ 调整拆分边界 / 拿不准呈用户仲裁。

4. **派发**（命中下方三场景管制才派）：用 subagent 能力（实现用 general，调研用 explore）。**派发清单挂 omp Todo 逐项跟踪**（完成/打回可视化——SKILL.md「会话工作台」）。子代理 prompt 必须包含：spec 全文 + 工作目录（worktree 路径）+ "只做本子任务范围内的事；完成后报告：改动文件清单、验收命令运行结果、遗留问题"。**宿主兜底（TASKFLOW_GUARD F/G，v2.48.0）**：装了机制的项目，派发词引用 spec 路径（`.taskflow/<id>/subtasks/<n>/spec.md`）宿主即校验必填节并机械注入全文（引用缺失/空节 spec = 调用即红），edit/write 越出「涉及文件」清单宿主即警——但 prompt 仍按本条写全：宿主层是兜底不是替代，未装机制的项目只认本条。

   **子代理三场景管制（派发前必测，至少命中其一，否则编排层亲自做；借鉴 superdx）：**
   ① **并行任务**——≥2 个互相零依赖的子任务（无同文件修改、无输入输出依赖、无全局状态变更）；
   ② **第三者审查**——独立视角审查（merge.md 第 3 步 medium/large 审查、spec 对抗审查）；
   ③ **用户显式要求**。

   交互式步骤（理解与决策质询、方案确认、呈报）**NEVER** 派给子代理——子代理见不到对话语境，代答必跑偏。
5. **每个子任务完成后，编排层两阶段审查**（读其 diff：先 spec 合规、再代码质量；清单同 merge.md 第 3 步）。审查不过 → 打回子代理修（**同一阻塞项 3 轮不过 → STUCK升级门**，merge.md 第 3 步：换方案/收窄验收/revert 请用户拍板）；过了 → task.json 标 done。
6. 并行子任务的分支按 merge.md 末段合回任务分支；全部完成后走任务级 merge。
7. task.json subtasks[] 状态全程同步。
