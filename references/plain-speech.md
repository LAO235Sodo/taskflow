# 面向用户输出规范（PLAIN_SPEECH_GATE）

> 机制定义（SKILL.md 硬规则 24 / data.md 机制登记表）。本文件是细则唯一载体：双层要求、骨架选型、呈报稿模板、门脚本用法、词表维护。
> **范围边界（2026-10-10 拍板，对抗审查自检实证后显式化）**：本门只管**面向用户的呈报稿**（briefing-*.md 五类）——技能内参考文档与 CHANGELOG 不检（自检跑 stages.md/近四版 CHANGELOG 得 80 红，属文风债非门缺陷；技术散文另立阈值成本不成比例，不立）。
> 防的事故类：面向用户的方案/分析/说明满篇未解释行话与名词定语堆栈，人类读不懂（2026-10-09 用户实证「定语看不懂，也不知道描述什么」）；以及反向病——只剩大白话却没有结构，内容一长无从下手（2026-10-09 用户同轮拍板「还必须有足够的结构化输出」）。

## 1. 双层要求（骨架 + 血肉，缺一不可）

| 层 | 管什么 | 合格线 |
| --- | --- | --- |
| 骨架层（结构化） | 一份输出的组织方式 | 按内容形态选骨架（见 §3）；结论先行段 + 待拍板项独立成节；多维事实禁埋进段落流让读者自行拼装 |
| 血肉层（叙事体） | 每一句话怎么写 | 完整因果句（谁、对谁、做了什么、所以怎样）；术语与行话**首次出现先给一句大白话再挂术语**；白话但不含糊（见 §2） |

两层各管一档：表格/清单做骨架，格子内用叙事句子展开——结构给全貌，句子给因果，不能拿其中一层替代另一层。

## 2. 血肉层规范（叙事体句子）

- **结论先行**：第一句就是答案或判定，然后再展开原因和细节。
- **术语首现带白话**：`DEPLOY_GATE（部署协调门：防止两个任务互相覆盖部署）`——括号里的话从 data.md 机制登记表「大白话」列或 glossary.md 抄，不自造口径。
- **白话 ≠ 含糊**：「页面乱了」不合格（没说清现象与因果）；「列表页下滑后再返回，位置回到了顶部」合格。含糊的根治是硬规则 12 的术语化记录，面向用户只是换成因果完整的人话，不是降级成模糊语。
- **禁**：电报式短句堆叠；名词定语堆栈（❌「并集收口载体上的签名册顺位改号」）；未解释的机制代号裸奔（I16、DEPLOY_GATE 不带括号直接出现）。

## 2.5 段落纪律与装饰克制（2026-10-09 用户截图实证——「长句没分段没逻辑分层」「喜欢写横幅」）

**段落纪律**（治"每句都合格但堆成一坨"）：
- 一段只装一个中心意思，不超过 4 句；超过就拆段，或者改写成列表（列表本身就是分段手段）。
- 因果链超过两跳（A 导致 B、B 又导致 C、C 造成 D）必须列表化，禁塞进一个段落让读者自己理顺序。
- 段与段之间要有承接词或递进关系，不是把一段硬掰成两段了事。

**装饰克制**（治"三重装饰"）：
- emoji 标题每份输出最多 1 个，且仅用于真正的清单/多节内容；短回复（三四段以内）不设标题、不用 emoji。
- 禁装饰横幅线（`─────`、`═════` 之类连续符号线）——分节靠标题或空行，不靠画线。
- 一份输出最多一种骨架装饰：要么表格、要么列表、要么分节标题，不叠用两三套。

## 3. 骨架层规范（结构化选型）

| 内容形态 | 骨架 | 说明 |
| --- | --- | --- |
| 两个及以上候选/方案/版本的对比 | 表格 | 列 = 对比维度，行 = 候选；结论写在表格前 |
| 并列事项（清单、步骤、改动点） | 编号清单 | 每项 1–3 句叙事展开，禁光秃名词 |
| 有先后顺序的流程 | 步骤列表 | 每步写清入口与出口 |
| 单点事实/机制解释 | 短段落 | 一段一个中心，超过两段就该考虑升级骨架 |
| 需要用户拍板的呈报 | 固定模板 | 见 §4 |

问答类答案尾部固定附证据自检行（J22 证据源分级，格式定义见 qa.md「带证作答」节）。**档位收口行（2.78.2——字段式机械约束；两轮散文加厚实证不足：T2 复测模型对齐后仍抛「修复方向（供拍板）」A/B 并列段）**：理解型/模糊信号档（qa.md J27 意图档位判定）的答案尾部、证据自检行之前，固定附一行必填字段：`档位：理解对照｜你的理解与实现一致吗？（一致→无需动作；不一致→指出差异点，我们立项）`——收口问句由模板强制，不依赖模型自觉，**缺失可打回**（与证据自检行同款抓手）；同档骨架**禁含「方案/方向/建议」类段落或字段**（含「修复方向（供拍板）」式 A/B 并列段——出现即违反 J27）；改动型档不受此限（正常改动流程）。

任何超过 ~300 字的输出必须至少有一个显式骨架（标题分节 / 表格 / 清单之一），纯段落流 = 不合格。

## 4. 呈报稿模板（briefing-<场景>.md）

五类正式呈报（方案呈报、打回返工呈报、升级确认门/需求变更门呈报、验收简报、部署清单）呈报用户之前，先落稿到 `.taskflow/<id>/briefing-<场景>.md` 并过门（§5），绿了才呈报。稿子结构：
报进度 / 所处环节统一用 `references/stages.md` 的节点名（节点自带使用者定义，呈报里按已定义词汇直接用，不另展开）。

```markdown
# <一句话结论——用户只读这句也能做决定>

## 背景（为什么现在谈这件事）
2–3 句因果链：现象 → 原因 → 所以需要拍板/知晓。

## 主体（按 §3 选型：对比用表格 / 并列用清单 / 组合用矩阵）
每格 1–3 句叙事展开；术语首现带白话括号。

## 待你拍板
- 选项 A：<一句话>——代价/收益
- 选项 B：<一句话>——代价/收益
（或「无需拍板，知悉即可」）
```

落稿是给门检的，不是给用户看的最终格式——对话里照稿转述（保持骨架），稿子留档供追溯。

## 5. 门脚本（validate-plain-speech.mjs）

```bash
node <skill目录>/assets/harness/validate-plain-speech.mjs <呈报稿.md> [<更多稿>...]
```

1. **行话裸奔**：行话词出现，且前后 2 行内无任一锚词 → 红（glossary.md 锚词列定义）。
2. **代号裸奔**：ASCII 机制代号（如 `DEPLOY_GATE`、`I16`）出现，且同行代号后 80 字符内无括号解释 → 红。
3. **超长句（双粒度）**：剥行内代码后，细粒度单句（逗号顿号括号级切分）>60 字 → 红；句号级单「句」（。！？切分）>80 字 → 红（v2.46.1——治冒号/破折号/括号串联的"一句写到底"，细切会把它拆成合格碎片漏检，真样本实证）。
4. **段落堆叠**：连续文本块（非表格/非列表/非标题/非代码）内句数超过 6 句或总字数超过 200 → 红。
5. **装饰横幅**：整行由连续装饰符号（`─ ═ — = - *` 等 8 个以上）构成且非表格分隔行 → 红。
6. **列表项堆叠**（v2.47.0）：列表项内超过 3 句或 150 字 → 红——列表行被段落检测豁免后项内无约束的盲区（对抗审查实证）。
7. **无骨架**（v2.47.0）：纯段落总字数 >350 且全文无表格/列表/分节标题（≥2 个标题）→ 红——每段独立合格但整体零结构的绕过（对抗审查实证）。
8. **emoji 标题滥用**（v2.47.0）：带 emoji 的标题行 >1 → 红——规范"每份输出 ≤1"的机械化。

代码块（``` 围栏）与行内 `` ` `` 片段不检测；引号（「」“” 与半角双引号）内内容豁免行话/代号检测（引用/列举场景）。退出码 0 = 绿，1 = 红（逐条列出行号与违规类型）。

**已知边界（防错不防骗，对抗审查定稿）**：故意把行话包进引号或行内代码可绕过词表检测、锚词出现在无关语境会误命中、行话变体（改一个字）永远追不完——门防的是诚实作者的错误，不防故意绕过者；后者的防线是流程（呈报稿留档可审计）与人工复核，不是文本检测。

边界（诚实条款）：门抓的是**可机械检测的不可读信号**，不是「人类理解度」本身——不含行话的句子仍可能难懂。最终回路是用户反馈「看不懂」→ 经验归纳 → 新行话进 glossary.md / 收紧检测，每次反馈都在收紧系统。

## 6. 词表维护（新行话登记）

- 新机制/新行话写进 SKILL.md 或 references 时，同一变更在 glossary.md 登记一行（行话 + 大白话 + 锚词）；机制类在 data.md 机制登记表「大白话」列填一句人类解释（lint 检查非空）。
- 技能级**自造词**统一登记 references/terminology.md「术语对照表」（自造词 → 传统术语 → 一句话定义）——能用传统术语直呼的直接直呼（扳机=触发器、搁置=挂起、归层=归档）；确需自造须先入表再使用，文档/输出首现写「自造词（传统术语）」。
- 锚词选白话里最具区分度的 2–3 个短语；宁可放过（假绿），不可误拦（假红）。
- 用户对某个表述反馈「看不懂」且词表未覆盖 → 该词当场登记，这正是归纳回路的落点。

### 项目词表（可选层，v2.43.1）

项目侧行话（技能词表管不到的领域词，如部署记录表名、业务探针名）登记在 `<项目根>/.taskflow/glossary.md`，格式与技能词表相同（行话/大白话/锚词三列）。门脚本从被检稿路径向上自动发现该文件：存在即合并加载（**项目词覆盖同名的技能词**），不存在则静默只用技能词表——零配置门槛，各项目按需生长。用户对项目术语反馈「看不懂」→ 当场登记进项目词表，回路同技能词表。

### 白话可迭代（2026-10-09 用户拍板）

词表不是一次登记定终身：用户对**已登记词条的白话**仍反馈看不懂 → 当场**改写该词条**（大白话与锚词一起换，换到用户能理解的风格为止），禁另开重复词条。项目词表（.taskflow/glossary.md）改完下一轮请求即被 TASKFLOW_GUARD E 注入吸收（活读）。
