# 问答管线（提问类输入：回显理解 → 定向探索 → 带证作答 → 追问衔接）

> 触发：SKILL.md 意图识别表「问代码/领域问题」行（求解释/现状/位置/可复用性，非改动描述、非任务进度）。硬规则 15 的细则载体。**判定动作外显**：`识别为〈问答〉——〈依据〉`。答案的叙事体与结构化双层要求统一走 PLAIN_SPEECH_GATE（硬规则 24，细则 references/plain-speech.md——本文件的骨架规范是其问答实例）。

## 为什么问答要走管线（反面实证）

提问类输入曾有两条死路：

- **不触发**：触发词无「提问」→ taskflow 不加载 → 编排层裸奔：自己搜代码直接作答。理解过程黑盒，用户无法分辨「模型没理解我」还是「代码本来如此」。
- **边搜边脑补**：静默选定一种解读 → 搜索与回答全部建立在这个解读上 → 产出后锚定，事后纠正要对抗锚点，比事前对齐贵。

用户实证（2026-09-26）：增量问答（先问「做了什么」再问「怎么改/能不能复用」）反而更准——机制 = **理解先外显、先纠正、指代落地**（「这里」从猜测变成双方都看过的具体代码）。本管线把该机制从第二轮前移到首次回答。

## 第 1 段：理解回显门（CRITICAL——回显先于探索，禁止先搜后答再补理解）

**答案的第一句话必须是理解回显，不是探索结果**：

> 你问的是〈X〉，我指向〈对象/范围〉，按〈口径〉作答。

- 回显里任何一处多义 → 硬规则 10（列候选口径请用户选 / 纯查询分口径并列作答）
- **口径层判定（功能/页面类问答必过，2026-09-30 枚举字段问答实证并入）**：功能/页面类问答（「XX 怎么填充/怎么工作/怎么用/什么效果」）的「口径」必须先辨两层——**数据口径**（选项来源/字段落库/契约链路）vs **交互行为口径**（用户操作→状态变化→退出重进等生命周期）。凡指向产品功能的「怎么填充/怎么用」类动词，交互口径优先作答或双口径并列请用户选，**禁止默认只答数据链路**——话语命中实现词汇 ≠ 用户诉求在实现层（实证：问「分类怎么填充」，按数据口径答了字典端点+落库，用户真实诉求是「选了没传退出会怎样」，多走两轮才命中；兜底依硬规则 10「判不清按多义」）
- **意图档位判定（判定点 J27：认知对齐优先，方案悬置；2026-10-24 用户高频场景实证）**：口径层判定之后、探索之前先辨意图档位——用户是在**对照自己的认知**还是**发起改动**。防的两层错误：①跳过认知对齐直接出方案（用户可能对齐后发现自己理解与实现不一致、根本不想改，方案白出）；②方案建立在用户过时认知而非实际实现上。**理解型（含认知对照）**：话语信号=「怎么实现的/为什么这样/是不是这样/和我理解的一样吗/之前是怎么做的/忘了」→ 回答止于：实际实现呈现（代码锚+链路，按 J22 证据源分级）+ **与用户认知的差异点主动对照**（反直觉实现/历史拍板导致的特化/易误解点，逐点标注「实现是 X——与『常见预期 Y』不同，原因是 Z」）；**禁主动附方案/改动建议/「建议优化」——包括多方案并列呈报**：理解型与模糊档位下『先对齐、方案悬置』无例外——对齐完成后唯一合法收口=确认问句（「实现与你的理解一致吗？要调整的话我们再立项」或等义问句），不出现任何以「方案」为标题或实质的段落（T2 锚例：模糊信号「感觉排序有点问题，是这样吗」模型先对齐后主动抛三个修改方案，辩称「对齐后呈报方案请你拍板」符合 J23——J27 与 J23 适用边界不明被突破，本句钉死）。**J23 方案内取舍拍板仅适用已立项任务**，理解型对话不适用——对齐后用户显式发起改动才立项，立项后才有 J23。落地结构=答案骨架的**档位收口行**（plain-speech 骨架必填字段，缺失可打回）——收口问句由模板强制，不依赖模型自觉。结尾收口固定句式：「实现与你的理解一致吗？要调整的话我们再立项。」——把「改不改」显式交还用户。**收口的合法与禁止形态（2.78.4——第四轮复测实证：收口段混杂两种性质，「问偏好」与「方案推销」的分界明文化）**：**合法（问偏好）**=纯问题形式——「你希望按哪个基准/哪种效果？」「你的理解是这样的吗？」；判别法：选项里**不含**实现路径、改动成本、推荐标注、立项承诺。**禁止（方案推销）**判别法——四特征任一即禁止（包括包成「口径选项」外形的）：①「推荐方向/推荐」标注；②改动面/成本描述（「只动前端」「零契约变化」「要推翻既有拍板」）；③立项承诺（「选好我就立项走」「按 taskflow 立项后真机复验」）；④「顺带建议」（「可以加一行小标识」）——理解/模糊档下一律禁止：方案选项属于立项后的决策质询（J11/J23），在理解档前置=抢占用户的「要不要改」决策。第四轮实证反例：「要不要改取决于你想对齐哪个基准：1. 卡片改显分享时刻（推荐方向）2. 排序改回创建时间 3. 保持现状。你选 1 或 2 我就立项走」——包成「口径选项」外形，①②③齐备，仍是方案推销。**标准范例（用户拍板锚例，原话入册）**——理解档的标准回答形态：「实际情况是：排序按分享时间走，但卡片上显示的是上报时间，两个时间对不上，所以看起来乱。你的理解是这样的吗？如果看完你确实想调，跟我说一声，我们走正式流程——到时候再谈具体怎么改。」特征四条：①摆事实（带代码锚）；②问理解（一句确认问句）；③说明存在后续路径但不展开（「我们走正式流程」一句话带过，禁展开方案内容）；④**重点前置、决策零负担（直白可速断）**——第一句就是结论/差异点（不是铺垫），用户读完即可拍板「一致/不一致」，无需自行归纳；判别法：用户读完第一句和最后一句，就能完成对照与决策——中间全是支撑，没有需要消化的推销或术语（用户评价：「能让我一下子抓住重点」）。**改动型**：显式改动信号（「把 X 改成 Y」「加个 Z」「这里不对要修」）→ 正常走改动流程（R01/R02），不受本判定拖慢。**模糊信号防呆**：话语含弱改动信号（「是不是有 bug」「这样对吗」「感觉不对」）→ 仍先认知对齐（呈现实现+差异对照），方案悬置；用户基于对齐后认知显式发起改动才走流程（对齐本身就可能消除「假 bug」——用户以为的 bug 是特化设计）。**定性跳转门（2.78.3——第三轮复测实证：模型查出真 bug 后以「已确认缺陷」自我授权直接进入「修法建议（待拍板）」，「模糊→确认缺陷」的定性跳转绕过悬置，J27 无此边界条款）**：排查中查到疑似缺陷证据（数据实证/复现步骤）时，模型单方宣布「确认属实/确认是 bug」**不改变档位**——合法动作=呈报定性证据并请用户确认：「查到 X 证据，疑似〈缺陷描述〉——确认成立的话我们立项修」；**确认前修法/方案仍悬置**（含单修法与「顺带建议」形态）。用户确认缺陷成立 → **直接立项**（走正常流程），立项后才进方案与 J23 方案内取舍——即「定性证据 → 用户确认 → 立项 → 方案」的合法顺序，方案不允许在立项前以任何形态（含单建议）前置。锚例（本轮实证）：「79% 情报排序键同微秒」是出色的定性证据——正确行为=呈报此证据+收口「确认是缺陷的话我们立项修」，而非同段给出「加 tie-breaker」修法。与第 4 段「问题实为需求描述→转新任务」兜底**对称**：那边防把需求当问答，这边防把问答当需求前奏——两者并列为意图档位判定的两翼
- **豁免档（类型制，2026-10-24 收窄——「一行能答」不是豁免判据）**：仅「定义/位置/指针类」问题（答案=纯文件:行号指向、零行为断言）可豁免——回显压缩成答案首行（「你问的是 X——在〈文件:行号〉」），错了用户自然会纠正。凡含「有没有/会不会/支不支持」类**行为断言**的问题一律不豁免，哪怕一行能答也须走完整管线（教训锚例：J22 翻车问题「科长有没有同事情报入口」恰是一行能答——一行答出的是推断）
- 回显被纠正 → 按纠正后的口径走第 2 段，不辩解不锚定原解读

## 第 2 段：定向探索（按问题卡探索，不漫搜）

探索前先答三问，答不出就先补齐再搜（**第 0 问 = 第 1 段口径层判定**——功能/页面类问题先定数据/交互口径层，口径层选错则探索方向全错）：

| 三问 | 内容 |
| --- | --- |
| 搜什么 | 符号 / 字段 / 路由 / 报错文案（标准术语，硬规则 12） |
| 在哪搜 | 目录 / 文件线索 / 命中信号的领域词 |
| 什么算答对 | 判定标准（找到什么才算回答了用户的问题） |

- 技能联动：按 domain.md 生命周期阶段表「问答」行加载（代码导航 / 外部调研 / 需求溯源各有正主）
- 硬规则 13/14 照常适用：渲染事实采样定案，不目测定案；答案涉语义行为先盘消费方，不凭单点代码下「全链生效」结论

**功能边界类问答的统一源路由（DOC_SYNC_GATE 读侧，硬规则 26；2026-10-10 拍板）**：问题命中功能边界特征词（能不能 / 谁可以 / 什么状态 / 什么权限 / 边界 / 功能在哪）→ 第一步查**项目统一源文档**（路径由项目 conventions.md「统一源」节登记，未登记则跳过本路由直接走代码探索），以它为答案基准作答；统一源未覆盖的再查代码，并**把查到的边界回写统一源**（读侧反哺写侧——地图越用越全）；统一源与代码冲突时按「数据类问题以运行中服务为唯一事实源」既有铁律处理（代码为准、回写修正统一源）。防的病：每个边界问题都现场翻代码（没有一处查全部的地图）+ 功能改了文档没人强制跟着改（写侧门治本、本路由治标引流）。

**口径类问答的条目锚核对（REQ_ANCHOR_GATE，可选增量——非本门承重）**：作答引用了 PRD 条目编号（如 F-XX-NN / US-XX-NN）→ 顺手 grep `docs/prd/**` 确认条目标题真实存在（防读侧引用幽灵条目，误导后续 spec 挂锚——REQ_ANCHOR_GATE 的锚存在性检查会拦，但读侧先核省一轮返工）；条目不存在 → 如实注记「查无此条目」并列最接近条目，不猜号。

## 第 3 段：带证作答

结构固定：**结论一句话 → 主体（按答案形态选骨架）→ 不确定性与边界 → 证据自检行**。

**证据自检行**（2026-10-23 拍板：J22「实证/推断分标」从行为要求升级为输出结构，缺失肉眼可查可打回——与 J19「影响面：已核 N 处」同款抓手）：答案尾部固定附一行证据构成，格式（四槽，2026-10-24 扩——外部事实答案（J14 官方文档原文）与文档级答案有合法槽位）：`证据构成：代码实证 N 处（文件:行号 列举）｜实测 M 项｜文档 D 项（来源：URL/prd 条目）｜推断 K 项（逐项标注，未验证）`；全实证无推断写 `证据构成：代码实证 N 处（…）｜实测 M 项｜文档 D 项，无推断`。**对应性纪律（2026-10-24 补）**：自检行所列锚必须是正文实际引用且支撑对应结论的锚；正文关键断言无锚不得计入实证 N，装饰性列举按虚报论。豁免档仅限第 1 段类型制豁免（定义/位置/指针类），其余一律附自检行。

**证据落痕分级（2026-10-22 企微端口映射事故实证——凭记忆断言「可信域名不支持端口、必须锁死 443」，被用户一句「这是验证过的吗」戳穿，官方文档原文相反：带端口显式支持（`mail.qq.com:8080` ✓）；教训=查证顺序在被质疑前，不在被质疑后）**：

| 断言类型 | 证据要求 | 禁止 |
| --- | --- | --- |
| 仓内事实（代码行为/配置/流程） | 文件:行号（既有纪律不变） | 无落痕的机制断言 |
| **外部事实**（第三方系统行为：产品配置规则/官方 API 语义/协议约束/平台限制） | **官方文档原文或本人实测复现，附来源 URL——查证动作在作答前完成**（web_search 官方文档；research 技能=外部信源调研正主，domain.md 问答行已挂） | 凭「文档记忆/社区普遍经验/印象」给确定性结论 |
| 推断（查无官方信源或查证成本明显过高） | 显式标注「推断，建议验证」+ 附验证方法（找谁确认/怎么实测） | 「必须/一定/不可能/规范决定」类确定性措辞；用表格/规范引用包装推断 |

**触发判据**：回答中将包含对第三方系统行为的确定性断言（「X 不支持 Y」「X 会拒绝 Z」「X 的规则是 W」「必须用 X 不能用 Y」）→ 即入本门，先查后答。**自检一句话：这句话拿去跟外部团队谈判/写进方案，错了谁担责？——担责的断言必须带信源。**

**证据源分级（判定点 J22；2026-10-23 同事情报可见性问答实证——矩阵答案「科长：同上（也有同事情报列表）」格是链式推断（由已证事实逐跳推出、未逐跳独立验证的结论）：从「可见性服务会放行」推「UI 有入口」，未验证科长形态 TabBar（注释明写「无我的情报无门店」，一次 grep 即可实锤），用户实测把自己设成科长进页面打脸：根本没有「同事情报」入口。教训原话：「代码是最有力、最明确的，但回答我的时候不是基于代码回答我。」）**：

- **强度序**（证据可信度排序）：运行时实测（用户观察/截图/实际操作结果）> 代码实证（grep/read 到的渲染条件、路由、后端判定）> 统一源文档（docs/prd 等——设计意图可能过时）> 链式推断。功能/行为/现状类回答必须基于可用最高强度证据源；**代码可查的问题禁用推断作答**——推断只允许作为「待验证假设」显式标注后走查证。
- **一跳一实证**（链式推理的每一跳都独立查证，才能作为结论）：锚例：「可见性服务放行」≠「UI 上有入口」——后端判定与前端呈现是两跳事实，只用第一跳答第二跳=翻车（即本判定点案例）。
- **实证/推断分标**：已实证项带文件:行号锚；未能验证的项显式标「推断，未验证」——禁混排成同一确信度（案例矩阵里实证格与推断格外观无差别，用户无法分辨哪格是猜的）。落地结构=答案尾部证据自检行（见本段骨架行定义），缺失可打回。
- **实测优先**：用户实测观察/截图与模型结论冲突 → 用户观察优先，立即重新查证后修正，禁辩护旧答案（案例第二轮用代码纠正并发现真实盲区=正面示范）。**反向分支（2026-10-24 补）**：重查后代码与用户观察仍冲突 → 呈现两造证据（代码锚 vs 观察复现步骤/环境差异）请用户复核操作路径——禁坚持旧结论，也禁无实证顺从改写结论（顺从不是实证，改写后的结论同样要能落到锚上）。

**主体骨架（2026-09-30 实证扩展：首尾三段式只管结论与边界，主体无规范则场景一多退化成段落流）**：

- 单点事实/机制解释 → 短段落，一段一个中心。
- **≥2 个并列场景/分支/条件 → 先骨架后血肉**：先用编号清单或矩阵表格（场景 × 条件 → 结果）给出全貌，再逐格用 1–3 句叙事展开；多维组合真相**禁止埋进段落流让读者自行拼装**（实证：三场景×两路径=6 格真相用叙事承载，用户判「内容很乱、逻辑不清晰」；同会话同类内容改用表格后清晰度立判——病灶在主体骨架缺失，非叙事体本身）。
- 存在对比维度（如「两种退出路径」）→ 优先矩阵表格。
- 证据落痕（文件:行号）跟在各结论格之后作锚点——不混在长句中间切碎句子，不集中堆文末。
- 与项目「叙事体、表格仅限数据对比」拍板兼容：矩阵/清单做骨架（结构），格子内叙事解释（血肉）——多场景×多条件对比正是「真正的数据对比」。
- 双层要求统一载体：血肉层（叙事句子、术语首现带大白话括号、代号禁裸奔）与骨架层选型表见 references/plain-speech.md（PLAIN_SPEECH_GATE，硬规则 24）。

- 证据 = 文件:行号 + 关键代码/数据摘录；**无证据的结论必须标注「推测」**（硬规则 15），推测不得写成定论语气
- 表述精确但用人话：现象 + 根因 + 依据的因果链必须完整（硬规则 12 精神——禁「那个地方有点乱」式含糊），同时行话首现带大白话、句式叙事化（PLAIN_SPEECH_GATE 血肉层）
