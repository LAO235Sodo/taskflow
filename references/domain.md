# 领域技能联动

taskflow 管任务流程，专业判断交给领域技能。写 spec 时检测领域，实现阶段注入，审查阶段复检；**需求变更经 `req-confirm` 时再复核一次**（变更后领域可能漂移——纯后端任务中途加前端页面即漏检，2.69.3 补）。

**领域检测**（写 spec 时做一次，拆分时复核）：

| 信号 | 领域 |
| --- | --- |
| 需求含 页面/组件/样式/布局/交互/界面/仪表盘/落地页，或文件以 .tsx/.jsx/.vue/.svelte/.css/.scss/.html 为主 | 前端 UI |
| 需求含 接口/API/服务端/后端/数据库迁移，或改动以服务端代码为主 | 后端 API |

- **全绿** → 按映射表注入；
- **有缺** → 把缺失清单（一句话用途 + 安装方式）呈给用户**选择安装哪些**——安装是网络动作，逐个确认后才执行；用户不装 → 该领域后续审查如实注记「未经 XX 审查」，**不假装在**；
- 装源未知（`npx skills add` 不留 remote，无法溯源）→ 注册表该条标「待补」，用户提供仓库地址后填入 `scripts/skills-registry.json` 的 `install` 字段即永久生效；
- 检测扫描四个标准安装位：`~/.config/opencode/skills`、`~/.agents/skills`、`~/.claude/skills`、`~/.omp/agent/skills`（可用 `TF_SKILL_DIRS` 覆盖）。

实现注入方式：编排层用 skill 工具加载后，把要点摘录进 spec / 子任务 spec 约束节，并随 prompt 传给子代理（子代理自身具备 skill 能力则直接加载）。

**前后端职责判定**（spec 阶段做一次；跨界功能的分工线必须显式写进 spec「边界与影响面」节，不靠实现时临场发挥）：

| 逻辑归属 | 判定 | 本项目实证 |
| --- | --- | --- |
| 数据真源 / 落库 / 幂等 / 事务 | **后端** | upsert 幂等（summary v2） |
| 可变选项集/字典值域（品牌/车型/分类等运营会增删改的业务枚举） | **后端**（字典表 + 只读端点 = 单真源；前端运行时拉取 + 内存缓存，禁固化进 bundle——变更 = 改库即生效，不发版） | dx_dict_* + /dict 端点（前端下拉/后端校验/AI prompt 三消费方共真源） |
| 聚合 / 统计口径 / 时间窗计算 | **后端**（口径唯一；前端只渲染） | KPI 后端算、SummaryCard 前端渲染 |
| 权限 / 越权校验 | **后端**（前端呈现隐藏不是安全边界） | reporter 范围 SQL（replay-my-failed） |
| 外部 API 与凭证 | **后端** | 百度逆地理后端调（upload-locate） |
| 纯呈现（格式化/条件渲染/动画/防抖） | **前端** | 「今日 N 条」仅 N>0 渲染 |
| 表单即时反馈 | **前端 UX + 后端复核**（前端体验、后端真源） | 编辑页校验 |
| **两侧都要** | **后端出结构化契约（版本化 JSON），前端 try-parse 降级**，契约测试锁形状 | `{"v":2,...}` + 回落纯文本 |
| 拿不准 | **默认后端**（可单测、可复用、换端不丢） | — |

**值域归属判别（上表「可变选项集」行的适用边界，防一刀切）**——判别问句：**「这个值域会不会在『不发版』的预期下被要求改变？」** 会 → 后端字典表 + 端点；与前端逻辑强耦合的枚举（值域变化必然伴随渲染/分支逻辑变化，如状态机三态）→ 前端常量合理；纯 UI 常量（文案/颜色）→ 前端。**后端常量/枚举类 ≠ 目标形态**——变化仍需重新构建部署后端，只是把发版对象从前端换成后端；目标是变更路径 = 改数据（一条 UPDATE 或管理 API 调用）。**静态固化是合法权衡不是违规**：数据量大 + 变更频率极低 + 前端消费复杂（级联/拼音序，如行政区划集）可选静态固化，但必须在 spec 注明权衡理由（变更频率 × 紧迫性 vs 数据量 × 消费复杂度），merge 阶段二据此核对。
跨边界功能**契约先行**：先定 DTO 形状（写进 `docs/design/*/api.md` + 契约测试锁）再动两侧代码；分工结论一行入 spec：「前后端分工：后端算 X / 前端渲染 Y / 契约 Z」。**深度判定加载 `api-and-interface-design`**（Hyrum 定律/契约思维，显式覆盖前后端边界划分——上表管快判，它管深究）。项目专属口径（如 AI 摘要的确定性边界）沉淀进 `decisions/`，scout 可检索。**需求含糊/发现自己在默默脑补时 → `interview-me`**（一次一问逼近 95% 置信再动工）；**large 档 spec 定稿前必跑 `doubt-driven-development`**（全新上下文证伪审查；medium/高风险改动可选）。

**前端任务的可视化呈报（硬规则）**：涉及前端页面/布局/视觉的任务，**方案呈报必须附可视化载体 + 呈报前完成「标准先行 + 真渲染自查」**（自查清单、六维核对、术语化规范与正反实证见 `references/prototype-selfcheck.md`），按改动类型选档（成本从轻到重）：

**前端任务的结构固化（DESIGN_SPEC_EXTRACT，硬规则 19）**：本表命中前端 UI 的任务，原型拍板后必须机械提取规格表（`extract-spec.js`：DOM 树 + 布局语义 + 全量 computed styles → `.taskflow/<id>/design/spec-extract.json` + `spec-extract.md`）；实现/派发/验收只认规格表，禁止凭记忆转述原型。

| 改动类型 | 合格载体 |
| --- | --- |
| 布局/结构排布 | **文字线框图**（ASCII 草图 + 尺寸/层级/区域标注，对话内直接给出）或 HTML 设计稿 |
| 已有页面修改 | **before-after 截图对比**（线上 vs 分支或 mockup）或标注截图（框选+序号，每号一句话） |
| 视觉/配色/真实效果 | **静态 HTML 设计稿**（自包含、真实数据样例、多方案并排）——必须真渲染，线框图不够 |

**纯文字描述 UI 方案 = 呈报不合格，用户可直接打回。**适用阶段：spec 方案呈报、续迭代方向建议（resume.md 第 10 步）、实现中途的方向变更。设计稿住址按 data.md「产物住址约定」（设计文档 `docs/design/<域>/` 进 git；任务内设计稿 `.taskflow/<task-id>/design/`——主仓库根相对——不进 git），路径随呈报给出；有 browser/截图工具时直接渲染呈现，不让用户自己找文件。实证：pl5android2 ui-visual-20260913 以 5 案并排 HTML 设计稿拍板「V2 淡·朱砂雾」，零误解一次过；反面实证：纯文字 UI 方案用户「比较难理解」（2026-09-19 用户原话）。**原型全流程六步链（现状基线→需求质询→对标引导→制作→交付迭代→裁决回写）与对标档位（⓪ App 现状基线 / A styleguide / B 对标拉范式 / C 风格库）唯一住处：`references/prototype.md`——前端 UI 任务建档质询与原型环节先读。**

**决策质询清单**（spec「关键决策」节怎么问；large 必跑，medium 仅对多解读项）：**处置分三档（可逆性分档，把问询压到真分叉）**——**逐项拍板**=贵翻项（新项目技术栈、系统架构、部署目标与环境、数据存储选型；个人开发语境下 spec 架构讨论=唯一设计评审机会，**架构项永不降级**）；**推荐+注记**=便宜可逆项（测试策略、外部依赖等，不问、可否决）；**既定，沿用**=建档时自动从 conventions/decisions/代码现状探测填入写出处，不进队列；档位判定机械锚：牵连计数跑 `tf.mjs impact`（grep 级）+ impact-analysis 技能/图谱工具（语义级）。借鉴主流（spec-kit clarify / BMAD tech-stack / superpowers brainstorming）共识：一次一问、选择题优先（2-3 候选+权衡）、推荐项置顶给理由、单会话 ≤5 问（影响×不确定性排序）、拍板即写回 spec 表格。**需求启发、缺口确认、决策拍板三类问题进同一个队列**（new-task.md 第 8 步「理解与决策质询」），理解类优先于决策类；故事收束前跑「覆盖度自检」（`templates/prd-user-stories.md` 六层清单：存在性/角色/名词完整性/规则生效语义/横切质量/时间轴；第 3-5 层 agent 自动扫描），缺口带候选+推荐进同一队列；不整批抛开放问句——整批开放问句等于把拍板负担整个甩回给用户。

**档位准入排除（判定点 J23「功能面取舍（feature-surface trade-off）归用户」——2026-10-23 chief-feed-entry 立项实证；J11 三档不变，本条是档位的准入排除面）**：**用户可见功能面的取舍禁入「推荐+注记」档，必须逐项拍板**——判定特征：该取舍改变用户直接可见的产品形态（复用既有组件的完整形态还是简化版、带不带既有提示/数字/徽标、砍不砍某个交互细节）。**成本论证是决策输入，不是决策授权**：「加这个要动后端契约/成本高」只改变呈报方式（两案并列对比成本、或建议分期），不改变归谁决定，禁用成本理由单方砍功能面。**单方裁剪=范围收窄，走收窄流程**：砍掉用户上下文隐含预期的功能面属范围收窄（SKILL.md 反馈分类「范围收窄」行既有纪律），须 spec 删验收项+PRD 回写+req-confirm 落痕——「spec 里留了可否决项」不满足收窄流程，不是补丁。锚例：chief-feed-entry 立项——科长页入口卡复用业务员页同款卡，模型单方决定「本期不带今日 N 条新分享数字」（理由：科室流无数据源，加数字要动后端契约），spec 留可否决项；用户推翻并拍板「这个也是要的」——这类取舍应进质询队列呈「A 带数字（动后端契约，成本 X）/B 不带（零后端改动）」请拍板，而非方案稿单方宣布。

**J23 判定特征两分与补充面（2026-10-24 对抗审查收窄，防「什么都逐项」稀释真拍板）**：①**砍/改既有用户可见功能面（含可达性）→ 逐项拍板**；②**全新界面设计细节（文案/loading/空态提示等）→ 归前端设计方向质询/原型确认，不逐项入队**。**可达性同属功能面**：入口深度、缺省可见性、feature flag 缺省值改变用户实际可达的功能面=功能面取舍（与决策组合门「含默认隐藏/折叠/抽屉态」同语义）。**原型确认=拍板载体**：原型/可视化稿确认即所见形态的拍板载体；简化形态过稿时须在稿面显式标注省略元素清单请确认，禁靠「没画到」静默省略。**上限不静默降档**：拍板项超单会话 ≤5 问上限时按影响×不确定性合并呈报，禁因上限静默降档。

**找茬自审（关键决策确认前，假设作者过度自信视角——v2.51.0；v2.53.0 补操作定义与档位解耦）**：命中三类高危决策——①跨模块修改；②编译器验不了的属性（并发安全/幂等/不变量）；③**不可逆变更（操作定义：git revert 够不着的外部副作用——外部库数据写删、已发布对外契约的破坏性变更、外部系统状态改写；分支内代码增删皆可逆不算）**——**任一处置档**（逐项拍板/推荐+注记/既定沿用；推荐+注记档命中三类高危禁入，须升呈用户）确认前自答三句：这个方案最可能错在哪？有没有未言明的假设？有没有未处理的边界？答案写进 spec「找茬注记」表（templates/spec.md 关键决策节占位），空白 = 质询不放行。
