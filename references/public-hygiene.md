# 公开仓卫生纪律（PUBLIC_HYGIENE_GATE 细则）

> 机制定义（SKILL.md 硬规则 29 / data.md 机制登记表）。本文件是细则唯一载体：原则、红线、替换规范、工作流、词表维护、事故处置、已知边界。
> **范围边界（2026-11-02 用户拍板，两层分离）**：本门只管**本技能公开仓自身的提交面**——用 taskflow 开发项目时，项目仓的 commit/merge/deploy 流程照旧走既有机制门，本门不进项目、不渲染到项目（mech 机制清单无此 token），项目开发侧零感知。

## 1. 为什么有这道门

- git 历史不可变：任何一行进了提交，就假设永久公开——后续提交只能让工作区变干净，洗不掉旧提交内容。
- 实证：v2.91.1/v2.91.2 两轮事后脱敏把工作区洗干净了，但约 40 个历史提交仍可回溯出项目名/公司词/工号路径，公开仓最终只能删库重建收场（2026-11-02）。
- 防线两层：纪律（本文件，供人读）+ 机械门（`tf.mjs hygiene` 命令与 release 链前置扫描，供机器拦）。

## 2. 原则

1. **历史不可变**——commit 即发布，敏感面在入库前拦，不靠事后清洗；
2. **默认公开**——写的时候假设全世界可读，而不是发布前再过一遍；
3. **词表单源**——黑名单唯一载体 `assets/harness/hygiene-terms.json`，扫描脚本只做引擎零内置词，禁把标识模式散抄进门脚本或文档（散抄=漏管）。

## 3. 红线四类（什么绝不进仓）

| 类别 | 涵盖 | 级别 |
| --- | --- | --- |
| 真名 | 公司、项目、系统、产品、内部域名的真实名称 | block |
| 个人标识 | 工号、用户主目录路径、内网账号 | block |
| 内网拓扑 | 内网 IP 段、内部域名、服务器路径 | block |
| 凭据 | 密钥、密码、token、私钥块 | block（视同泄漏处置） |
| 业务域词 | 行业专名、内部黑话（易组合定位公司） | warn（人工确认） |

## 4. 替换规范

- 真名 → 占位符（`<project>`）；硬编码个人路径 → 环境变量或 `<win-user>` 占位（先例：`TF_RELEASE_WIN_USER`，v2.91.2）；
- 示例数据 → 明显假的值：域名用 example.com、IP 用文档保留段 192.0.2.x、公司写「某主机厂」；
- **禁**「真名改一个字当假名」——假名必须无法反推真名；
- 机制说明需要举例时用类型描述（「某项目名」）指代，标识字面值只允许住在词表 JSON 里。

## 5. 工作流（触发点与命中处置）

- **触发点一（强制）**：release 链前置——发版自动全树扫描 tracked 面，block 命中=拒绝发版（fail-fast，先于任何写入动作）；
- **触发点二（自查）**：`node scripts/tf.mjs hygiene`（全树）或 `--diff [基线]`（增量，缺省对比 HEAD）；写完改动、push 前用增量自查；
- **命中处置**：block → 按 hint 改写或删除；确属误报 → 该行尾加 `hygiene-ok: <理由>`（理由非空，门放行并计数展示）；warn → 人工判断，保留需同样豁免标记；
- **新标识接入即登记**：接新项目/新系统，第一件事把真名/域名/IP 段登记进词表（block 级）再写代码——词表没有就扫不出，登记纪律是上游、机械门只是下游兜底。

## 6. 事故处置（发现已提交泄漏）

1. 未 push → 改写后重做提交（本地历史可废弃）；
2. 已 push 且仓公开 → **删库重建**：删远程仓 → 新 init 单提交干净基线 → 推回同名仓 → 各同步副本重新指向新历史（2026-11-02 实操配方；不用 filter-repo——远端 SHA 直链残留与 fork 无法保证清零）；
3. 凭据类 → 无论是否 push，先作废轮换凭据，再走第 2 步。

## 7. 已知边界（防自欺声明）

- 门只扫 git tracked 现值与 diff 新增行，**历史旧提交不在扫描面**——历史泄漏只能走 §6 处置；
- 词表不可能穷尽：新形态标识在登记前扫不出（§5 登记纪律兜底）；
- 提交者身份（author 姓名邮箱）是个人选择，不在词表管辖区，公开仓自行斟酌；
- 未跟踪文件不在 --diff 面（release 前置另有未跟踪文件红，双门合围）。
