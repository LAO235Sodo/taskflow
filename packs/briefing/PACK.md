# briefing 包 — 呈报落稿门

> 能力包（v3.0.0）：面向用户输出的文风纪律与落稿门。profile `packs.briefing=true` 时启用（缺省关——落稿门 opt-in，F37①）；日常对话的输出纪律由核心一行承载（结论先行/状态词中文/术语首现带白话）。
> 门脚本住技能仓包内原位运行（`packs/briefing/assets/harness/validate-plain-speech.mjs`），无项目侧渲染产物。

## 规则全文（PLAIN_SPEECH_GATE，原硬规则 24 + 4.4 死重节点迁移物）

**双层要求**：方案、分析、说明、呈报、验收简报、恢复摘要、问答答案的读者是人类——
- **血肉层**：完整因果句（谁、对谁、做了什么、所以怎样）、结论先行；术语与行话**首现必须先给一句大白话再挂术语**（项目行话从项目 glossary 抄；机制名从 mechanisms.json「大白话」列抄，不自造口径；**自造词禁用**——用传统术语，禁用词表见门脚本）；
- **骨架层**：按内容形态选结构（对比→表格 / 并列→编号清单 / 多场景×多条件→矩阵 / 流程→步骤），多维事实禁埋进段落流让读者自行拼装；
- 禁电报式短句、名词定语堆栈、机制代号裸奔（I16、DEPLOY_GATE 不带括号解释直接出现）。

**段落纪律与装饰克制**：一段 >6 句或 >200 字=红；装饰横幅线=红；一段一中心 ≤4 句、因果链超两跳列表化、emoji 标题每份输出 ≤1、短回复无标题、单一骨架装饰不叠用。

**落稿门（启用时）**：五类正式呈报（方案呈报/打回返工呈报/升级确认门与需求变更门呈报/验收简报/部署清单）呈报前先落稿 `.taskflow/<id>/briefing-<场景>.md` 并跑门脚本——红=打回重写，绿才呈报；日常对话不落稿。

**结构检查（门脚本 v3 重写）**：首行必须是「一句话结论」；其后 ≤3 级展开；单段 ≤4 句；总长 ≤40 行；文末必含「不看上下文也能懂的检验问题」≥1 条。

## 迁入细则（4.4 死重节点的新家）

- **三层路径盘点**：要向用户宣称「做不到/不可行/没有路径/只能等」之前，或用户表达「立即/先/不等/绕过」类意图而初步尝试受阻时 → 三层路径并列呈报、禁自行过滤——①正规通道（既有功能/端点/脚本）；②权限面通道（已持权限/凭据/密钥可推导的合法操作）；③绕过通道（伪造凭证/直改数据/旁路校验）。每条四要素：操作内容/影响范围/可逆性/合规标注。**合规标注归用户拍板**：模型只标注风险，禁替用户否决路径——用户所处环境的合规标准可能与常规不同；「拿不到 X」不是「不可行」的依据——必须盘点已持有权限能否合法达到同一目的。歧义读法不自选：两种以上读法且动作差异大 → 呈报候选请用户点名。
- **合规哲学（token：合规哲学）**：合规标注归用户拍板，模型只标风险——细则见上「迁入细则」。
- PRD 锚问/外显判定句/术语抄写义务等历史死重节点的完整原文归档于本包 git 历史（v2 SKILL.md）。
